ADP · AGENT DEVELOPMENT-STATE PROTOCOL

Why ADP exists

Six properties of git and the GitHub forge that were fine for one human on one branch, and are not fine for a fleet of agents. Each is stated mechanically, with a simulation you can step through. No familiarity with git internals assumed.

Created by Dov Zimring, with lots of help from Claude github.com/DeDuva/adp Apache-2.0 licensed
01 · GROUND FLOOR

What git actually stores

Git does not store diffs. It stores whole snapshots, addressed by the hash of their content. A file's bytes become a blob; a directory listing of blobs becomes a tree; a commit points at one tree plus its parent commits. The diff you read in a pull request is computed on demand by comparing two snapshots.

Two consequences carry through the rest of this page. First, history is a chain of complete snapshots, and a clone takes all of it. Second, the commit is the only record of a change, and its fields are fixed: author, timestamp, message, parents, tree. There is no field for why the change was made or how it was verified.

02 · PROBLEM

Operations scale with repository size, not working set

Because every clone carries the full object graph, the cost of starting work is a function of how large the repository is, not how much of it the task touches. A human pays that cost once per laptop. An agent fleet pays it once per attempt: every sandbox is a fresh machine with an empty disk.

This is the same wall Google hit at billions of lines, and the reason Piper is a centralized, DB-backed store with a virtual filesystem rather than a distributed VCS. Meta's answer, Sapling with EdenFS, made operations scale with the working set instead — proving git can be a facade over different internals.

03 · PROBLEM

The merge unit is a line, and a conflict is an error

Git merges by comparing three versions of a file line by line. When two changes touch overlapping lines, git cannot decide, so it writes conflict markers into the working tree and exits non-zero. For a human that is a prompt. For an automated pipeline it is a halt: the exit code propagates, the agent's next command fails, and the harness falls back to a retry-and-rebase loop it wrote itself.

Jujutsu showed the alternative: represent the conflict as a first-class object that can be committed and resolved later, so the pipeline continues and resolution becomes a task rather than an exception.

04 · PROBLEM

Speculative fan-out has no home in the model

The characteristic agent workload is N attempts at one intent: fan out, evaluate, keep the best, discard the rest. Git has no object for "attempt" and no lifecycle for a workspace. So orchestrators approximate it with branches, worktrees, or whole clones, and then have to garbage-collect them out of band. The 195 discarded attempts leave no trace, which means nothing can learn from them and no audit can see them.

Note that this is the one primitive with no GitHub analogue: a merge queue picks between changes that already exist as pull requests; it does not represent N competing candidate solutions to a single stated intent.

05 · PROBLEM

The server keeps no operation log

Git records the state of the tree, not the operations that produced it. A rebase does not modify commits; it creates new ones with new hashes and moves the branch pointer. The originals become unreachable. Locally you can sometimes recover them from the reflog, which is per-clone, expires, and is never pushed. After a force-push, the server has no record that the previous history existed, who replaced it, or why.

At one writer per branch that is survivable. With hundreds of automated writers it removes the two things automation needs most: an authoritative account of what happened, and a way to reverse it.

06 · PROBLEM

The change record has nowhere to put provenance

A commit's fields were designed for a person who could be asked what they were thinking. When the author is a model, the questions that matter are which model, which harness, which session, working from which prompt and which spec, verified how. None of those has a field, so each harness invents its own store: shadow repositories for checkpoints, memory files, session directories, trailers in commit messages. An organization running three harnesses gets three incompatible audit trails, none complete.

This is the pre-LSP editor situation exactly: every vendor reimplementing the same missing primitive, privately and incompatibly, until a neutral interface moved it behind a standard.

07 · PROBLEM

A green check is not evidence about the merged state

CI runs against the head of a branch. The thing that ships is the merge of that branch into a trunk that has moved since. Two changes can each pass, be textually mergeable, and still break in combination — one renames a field, the other adds a caller. Nothing in the git or GitHub model requires the evidence to describe the state that actually landed.

When agents write most of the code, verification rather than authoring is the throughput constraint, and this is the layer no current entrant leads with. It is also the hardest: evals are stochastic, so the gate has to be a statistical land criterion rather than a binary pass, or flakiness turns into queue collapse.

08 · SIDE BY SIDE

One task, both substrates

The same intent — enforce token scopes per route — run against a git forge and against an ADP server. Scrub the clock. The point is not that one bar is faster; it is where each lane spends time it cannot avoid, and what remains on the record afterwards.

10 · WHAT ADP IS

A typed transaction, and a server that gates on it

Every change is one signed record with four parts. Git compatibility is preserved throughout: git is the store, ADP sits beside the DAG, and git clone keeps working. The differentiating bet is the last two parts — binding context to verification evidence at merge time. Several efforts capture provenance; none gate on it.

INTENT
The task or spec the change is answering
DIFF
The change itself, in the git object graph
EVIDENCE
Tests, evals and benchmark deltas, bound to the merged state
PROVENANCE
Which agent, model, session; which human attested
WHERE IT STANDS

Working end to end and CI-verified: a Fastify + Postgres server with token auth, git smart-HTTP proxied to the real git http-backend, REST and GraphQL compatibility validated against the real, unmodified gh binary, a two-level land policy, push protection and DSSE-signed evidence bundles, and an append-only operation log with undo — written in the same transaction as the change it describes. A native MCP plane and a read-only web UI sit alongside the compat surface. Not yet built: the rest of the trust plane beyond push protection and evidence (org-enforced policy, dependency admission, scanner integrations).

The MVP target, met today: set three environment variables and an unmodified coding agent clones, reads an issue, edits, pushes, opens a PR, watches checks, gets a typed review and merges — against an ADP server, with no knowledge that ADP exists.
